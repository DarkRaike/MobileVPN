# Правила работы над проектом

## Назначение

Этот файл содержит обязательные правила для нейросети при работе над проектом Telegram Mini App и Marzban.

Перед началом любой задачи необходимо:

1. Прочитать этот файл полностью.
2. Изучить относящиеся к задаче разделы `tech.md`.
3. Быстро проверить структуру и существующий стиль проекта.
4. Только после этого предлагать или вносить изменения.

Функциональные требования, архитектура, модель данных и критерии приёмки находятся в `tech.md`.

## Основные принципы

- Писать чистый, безопасный и готовый к production код.
- Выбирать самое простое решение, которое остаётся тестируемым и поддерживаемым.
- Следовать существующей структуре, именованию и стилю проекта.
- Не добавлять абстракции, микросервисы, очереди и зависимости «на будущее».
- Не удалять важные исходные, конфигурационные, системные файлы, миграции и файлы развёртывания.
- Перед разрушительными или необратимыми действиями обязательно запрашивать подтверждение.
- Не вести длинные обсуждения, если можно безопасно сделать практический шаг.

## Порядок работы

1. Определить точную цель и критерии готовности задачи.
2. Найти связанный код, тесты, конфигурацию и документацию.
3. Понять причину проблемы или существующее поведение.
4. Внести минимальные связанные изменения.
5. Добавить или обновить тесты.
6. Выполнить доступные проверки.
7. Кратко сообщить, что изменено и как проверено.

Если информации недостаточно и предположение может существенно изменить результат, необходимо остановиться и задать конкретный вопрос.

## Архитектура

- Использовать модульный монолит SvelteKit.
- Держать доверенный серверный код в `$lib/server`.
- Разделять интерфейс, application use cases, бизнес-правила и интеграции.
- Маршруты должны выполнять только валидацию, авторизацию, вызов use case и формирование ответа.
- Использовать композицию и небольшие интерфейсы вместо наследования.
- Классы использовать только для инкапсуляции состояния или внешнего контракта.
- Расчёты и преобразования по возможности реализовывать чистыми функциями.
- Применять DRY к бизнес-правилам, а не к случайно похожим строкам кода.
- Не удерживать транзакцию SQLite во время запроса к Telegram или Marzban.

## SvelteKit и Svelte

- Использовать TypeScript в строгом режиме.
- Для нового кода использовать Svelte 5 runes: `$state`, `$derived`, `$effect`, `$props`.
- Использовать `$derived` для вычисляемых значений.
- Использовать `$effect` только для синхронизации с DOM или внешней системой.
- Доверенные чтения выполнять через server `load`.
- Обычные пользовательские изменения выполнять через form actions.
- Webhook и нестандартные HTTP-контракты реализовывать через `+server.ts`.
- Использовать сгенерированные типы из `./$types`.
- Не отключать SSR без измеримой причины.
- Не создавать глобальное клиентское состояние, если достаточно `load`, URL или локального состояния компонента.
- Выносить реактивную логику в `.svelte.ts` только при реальном повторном использовании.

## Валидация и обработка ошибок

- Считать недоверенными все данные браузера и внешних API.
- Проверять во время выполнения данные Telegram Stars, Marzban, форм, URL и переменных окружения.
- Пересчитывать цену, скидку, валюту и срок подписки только на сервере.
- Использовать стабильные внутренние коды ошибок.
- Показывать пользователю безопасные и понятные сообщения.
- Не передавать клиенту stack trace, секреты, внутренние адреса и необработанные ответы провайдеров.
- Обрабатывать состояния загрузки, отсутствия данных, ошибки, успеха и повторной отправки.
- Не игнорировать ошибки без журналирования или явного решения.

## Аутентификация и права доступа

- Авторизовывать пользователя только по проверенному на сервере `Telegram.WebApp.initData`.
- Не использовать `initDataUnsafe` для авторизации и бизнес-операций.
- Проверять подпись Telegram, срок `auth_date` и структуру пользователя.
- Проверять права доступа в каждом защищённом серверном запросе.
- Давать доступ к админке только при совпадении проверенного Telegram user ID с `TELEGRAM_ADMIN_USER_ID`.
- Скрытая кнопка админки не считается защитой.
- Production-приложение не должно запускаться с тестовой или mock-аутентификацией.

## Платежи Telegram Stars

- Для цифрового VPN-доступа внутри Telegram использовать только одноразовые платежи Telegram Stars с валютой `XTR`.
- Создавать invoice link только на сервере через Bot API `createInvoiceLink`.
- Передавать ровно один `LabeledPrice`; цену хранить целым количеством Stars.
- Использовать непрозрачный локальный payment attempt ID в `invoice_payload` длиной не более 128 байт.
- Открывать invoice через `Telegram.WebApp.openInvoice()` только по прямому пользовательскому действию.
- Не выдавать VPN-доступ по callback `openInvoice`, статусу `paid` на клиенте или одному `pre_checkout_query`.
- Проверять webhook secret header, Telegram user ID, payload, `currency=XTR` и `total_amount`.
- Отвечать на валидный `pre_checkout_query` через `answerPreCheckoutQuery` не позднее 10 секунд.
- Выдавать доступ только после серверного `message.successful_payment`.
- Сохранять `telegram_payment_charge_id` с уникальным ограничением до запуска Marzban provisioning.
- Возврат выполнять через `refundStarPayment`; повторная обработка не должна повторно возвращать Stars или изменять срок.

## Интеграция с Marzban

- Обращаться к Marzban только из серверного адаптера по приватной Docker-сети.
- Не передавать Marzban credentials и внутренние API endpoints в браузер.
- Создавать или продлевать VPN только после проверенного Telegram `message.successful_payment`.
- Обеспечить идемпотентность по локальному ID заказа.
- Перед повторной попыткой сверять фактическое состояние пользователя Marzban.
- Использовать таймауты, ограниченное число повторов и backoff.
- Проверять структуру ответов Marzban во время выполнения.
- Не записывать полный Subscription URL в логи.

## SQLite и Drizzle ORM

- Использовать Drizzle ORM.
- Каждое изменение схемы оформлять версионируемой миграцией.
- Включить SQLite foreign keys, WAL mode и разумный `busy_timeout`.
- Хранить деньги целыми числами в минимальных денежных единицах вместе с валютой.
- Хранить время в UTC.
- Сохранять snapshot тарифа и скидки в заказе.
- Защищать уникальными ограничениями повторные payment events и бизнес-инварианты.
- Критические изменения заказа и промокода выполнять транзакционно.
- Проверять миграции на чистой базе и на предыдущей версии схемы.

## Безопасность и секреты

- Хранить секреты только в серверных переменных окружения или защищённых secret-файлах.
- Никогда не коммитить `.env`, API keys, токены, cookie, приватные ключи и webhook secrets.
- Хранить в `.env.example` только названия переменных без реальных значений.
- Ограничивать размер запросов.
- Применять rate limiting к авторизации, промокодам, поддержке, платежам и админке.
- Использовать параметризованные запросы через Drizzle.
- Удалять секретные данные из структурированных логов.
- Защищать cookie-authenticated изменения от CSRF.
- Использовать HTTPS и безопасные HTTP headers в production.
- Не публиковать Subscription URL в аналитике, URL страницы и сторонних сервисах.

## Качество кода

- Использовать понятные доменные имена без неочевидных сокращений.
- Писать небольшие функции с одной причиной изменения.
- Избегать `any`.
- Если `any` невозможно избежать, ограничить его локально и объяснить техническую причину.
- Комментарии должны быть краткими, полезными и на английском языке.
- Комментировать причину, инвариант или ограничение, а не очевидный синтаксис.
- Не оставлять мёртвый код и закомментированные реализации.
- Не оставлять TODO без связанной задачи или понятного объяснения.
- Не оставлять упоминания нейросетей и инструментов генерации в коде, комментариях, коммитах и PR.

## Тесты

- Добавлять тесты для каждого изменённого бизнес-правила и важного ошибочного сценария.
- Unit-тестами покрывать Telegram validation, скидки, деньги, переходы статусов, даты продления и идемпотентность.
- Integration-тестами покрывать Drizzle repositories, Telegram Stars pre-checkout/success/refund updates, admin authorization, ошибки Telegram и повторы Marzban.
- Критический путь от покупки до выдачи VPN покрыть end-to-end тестом.
- Тесты должны проверять наблюдаемое поведение, а не внутренние детали реализации.
- Исправление ошибки должно включать regression test, если это технически возможно.

## Обязательная проверка перед завершением

Выполнить доступные команды проекта:

1. Форматирование.
2. Линтер.
3. Type check.
4. Unit и integration tests.
5. Production build.
6. Проверку миграций, если менялась база данных.

Нельзя утверждать, что проверка прошла, если команда не запускалась. Если проверка невозможна, необходимо точно указать, что не проверено и почему.

## Git

- Использовать Conventional Commits.
- Писать сообщения коммитов кратко, на английском языке и в imperative mood.
- Один коммит должен содержать одно логически завершённое изменение.
- Автор коммитов: `DarkRaike <danikzhurik64@gmail.com>`.
- Не изменять историю Git и не выполнять destructive Git-команды без явного запроса.

Примеры:

```text
feat(payments): add Telegram Stars checkout
fix(webhooks): prevent duplicate provisioning
test(auth): reject expired Telegram init data
docs(deploy): document restore procedure
```

## Definition of Done

Изменение считается завершённым, только если:

- выполнены критерии приёмки;
- валидация и права доступа проверяются на сервере;
- обработаны ожидаемые ошибки и состояния интерфейса;
- добавлены необходимые тесты;
- format, lint, type check, tests и production build проходят;
- миграции и документация обновлены при необходимости;
- логи не содержат секретов;
- критичные изменения безопасности, платежей, Marzban и миграций проверены тимлидом.

## Приоритет инструкций

Если требования расходятся, использовать следующий приоритет:

1. Прямое актуальное указание пользователя.
2. Требования безопасности и критерии приёмки из `tech.md`.
3. Правила этого `AGENTS.md`.
4. Существующие соглашения проекта.

При конфликте нельзя молча выбирать удобный вариант. Необходимо сообщить о конфликте и запросить решение, если оно существенно влияет на результат.
