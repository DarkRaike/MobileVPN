# Техническое задание: Telegram Mini App для управления VPN-подписками

**Статус:** Draft  
**Версия:** 1.0  
**Дата:** 2026-07-27  
**Команда:** один разработчик и тимлид  
**Основной стек:** SvelteKit, TypeScript, Svelte 5, Tailwind CSS, SQLite, Drizzle ORM, Docker  
**VPN-контур:** Marzban, Xray-core, VLESS

## 1. Назначение документа

Документ определяет требования к веб-приложению, запускаемому как Telegram Mini App, и его интеграции с Marzban на одном сервере.

Приложение должно:

- безопасно авторизовывать пользователя по данным Telegram;
- показывать и продавать VPN-тарифы;
- принимать и учитывать промокоды;
- создавать и продлевать VPN-доступ через Marzban;
- показывать активную подписку, QR-код и ссылку подключения;
- принимать обращения в поддержку;
- предоставлять администратору компактную панель управления.

Документ ориентирован на реализацию одним разработчиком под ревью тимлида. Процессы, роли и инфраструктура, не дающие практической пользы небольшой команде, в первую версию не включаются.

## 2. Термины

- **Mini App** — веб-приложение, открываемое внутри Telegram.
- **Telegram user ID** — числовой идентификатор пользователя Telegram из проверенного `initData`. В переменных окружения и коде используется имя `TELEGRAM_ADMIN_USER_ID`; не следует называть этот идентификатор `chat_id`, если речь идёт об идентификации пользователя.
- **Администратор** — пользователь, чей проверенный Telegram user ID совпадает с `TELEGRAM_ADMIN_USER_ID`.
- **Тариф** — доступное для покупки предложение с названием, сроком и ценой.
- **Заказ** — намерение пользователя оплатить выбранный тариф.
- **Платёж** — запись о платёжной транзакции и её подтверждённом статусе.
- **Подписка приложения** — локальная запись о VPN-доступе пользователя.
- **Marzban user** — учётная запись VPN-пользователя в Marzban.
- **Subscription URL** — ссылка Marzban для получения конфигураций подключения.
- **VLESS** — основной протокол подключения, обслуживаемый Xray-core через Marzban.

## 3. Цели первой версии

1. Пользователь открывает Mini App из Telegram и автоматически проходит серверную аутентификацию.
2. Пользователь выбирает тариф, при необходимости применяет промокод и оплачивает заказ.
3. После подтверждения оплаты приложение создаёт или продлевает доступ в Marzban.
4. Пользователь получает ссылку подключения и QR-код.
5. Администратор управляет тарифами, промокодами и FAQ, просматривает обращения и основные операции.
6. Приложение и Marzban развёрнуты на одном сервере через Docker Compose с изолированными внутренними сервисами и HTTPS на публичных точках входа.

## 4. Вне объёма первой версии

- нативные приложения для iOS, Android, Windows или macOS;
- собственная реализация VPN-протокола;
- мультирегиональная инфраструктура и Marzban Node;
- несколько ролей администратора и сложная RBAC-модель;
- реферальная программа;
- автопродление с сохранением банковской карты;
- полноценная helpdesk-система с перепиской внутри Mini App;
- бухгалтерская, налоговая или фискальная интеграция до выбора платёжного провайдера;
- отдельное мобильное или desktop-приложение администратора;
- Kubernetes, микросервисы, очереди сообщений и другие инфраструктурные усложнения без подтверждённой нагрузки.

## 5. Пользователи и права доступа

### 5.1. Пользователь

Может:

- просматривать активные тарифы;
- создавать заказ и переходить к оплате;
- применять доступный промокод;
- просматривать собственный профиль;
- просматривать собственную историю покупок;
- просматривать только собственную активную подписку;
- копировать Subscription URL и показывать QR-код;
- читать FAQ;
- отправлять обращение в поддержку.

Не может:

- получать данные других пользователей;
- менять цену, скидку, срок или итоговую сумму с клиента;
- вызывать административные операции;
- напрямую обращаться к Marzban API.

### 5.2. Администратор

Администратор имеет все права пользователя и доступ к административному разделу.

Права администратора:

- CRUD тарифов;
- CRUD промокодов;
- CRUD FAQ;
- просмотр и изменение статуса обращений;
- просмотр заказов, платежей и состояния выдачи подписок;
- повтор безопасной синхронизации заказа с Marzban после ошибки;
- деактивация тарифа или промокода без удаления исторических связей;
- просмотр минимального журнала административных действий.

Право администратора проверяется на сервере для каждого административного запроса. Скрытие кнопки в интерфейсе не является контролем доступа.

## 6. Основные пользовательские сценарии

### 6.1. Первый вход

1. Пользователь открывает Mini App из Telegram.
2. Клиент передаёт исходную строку `Telegram.WebApp.initData` серверу.
3. Сервер проверяет подпись, `auth_date` и обязательные поля.
4. Сервер создаёт либо обновляет локальный профиль пользователя.
5. Сервер создаёт защищённую сессию.
6. Пользователь попадает на раздел «Главная».

Если проверка Telegram не пройдена, доступ к пользовательским данным и бизнес-операциям запрещается. Интерфейс показывает понятную ошибку и предлагает повторно открыть приложение из Telegram.

### 6.2. Покупка

1. Пользователь выбирает активный тариф.
2. Сервер загружает актуальную цену и срок из базы данных.
3. Пользователь при необходимости применяет промокод.
4. Сервер повторно проверяет промокод и рассчитывает итоговую сумму.
5. Сервер создаёт заказ и Stripe Checkout Session в режиме `payment`.
6. Пользователь завершает оплату на Stripe-hosted Checkout Page.
7. Сервер получает и проверяет Stripe webhook.
8. Платёж переводится в состояние `succeeded` один раз, идемпотентно.
9. Фоновая серверная операция создаёт или продлевает пользователя Marzban.
10. Локальная подписка синхронизируется с Marzban.
11. В профиле становятся доступны Subscription URL и QR-код.

Успех на клиентской странице возврата не подтверждает оплату. Единственным основанием выдачи доступа является проверенный сервером webhook либо отдельная серверная проверка статуса у провайдера.

### 6.3. Продление

- Если у пользователя есть активная подписка, срок тарифа прибавляется к текущей дате окончания.
- Если подписка истекла, срок прибавляется к моменту подтверждения новой покупки.
- Операция продления должна быть идемпотентной по идентификатору заказа.
- Повтор webhook или повторная синхронизация не должны добавлять срок второй раз.

### 6.4. Обращение в поддержку

1. Пользователь открывает «Поддержку».
2. Пользователь заполняет тему и описание проблемы.
3. Сервер валидирует и сохраняет обращение.
4. Сервер отправляет сообщение администратору через Telegram Bot API.
5. Пользователь получает номер обращения и подтверждение.

Ошибка отправки сообщения в Telegram не должна удалять уже сохранённое обращение. Запись получает статус доставки `failed`, ошибка журналируется, администратор может увидеть обращение в панели.

## 7. Структура и навигация Mini App

Приложение состоит из трёх основных секций:

1. **Поддержка** — слева.
2. **Главная** — по центру, открывается по умолчанию.
3. **Профиль** — справа.

### 7.1. Навигационный островок

В нижней безопасной области экрана размещается фиксированный навигационный островок в визуальном стиле Apple Liquid Glass:

- полупрозрачный фон;
- умеренное размытие содержимого под островком;
- тонкая светлая граница и мягкая тень;
- явно выделенный активный пункт;
- плавное, но короткое перемещение активного индикатора;
- иконка и доступная текстовая подпись для каждого пункта;
- адаптация цветов к Telegram theme params и системной светлой/тёмной теме.

Эффекты не должны ухудшать читаемость или производительность. Для устройств без поддержки `backdrop-filter` используется непрозрачный запасной фон.

Навигация поддерживает:

- нажатие на кнопки островка;
- горизонтальный свайп между соседними секциями;
- сохранение предсказуемого браузерного состояния;
- отключение или сильное сокращение анимаций при `prefers-reduced-motion`;
- отсутствие конфликта свайпа с вертикальной прокруткой и интерактивными элементами;
- минимальную область нажатия 44×44 CSS px.

Для первой версии допускается одна оболочка с тремя состояниями без трёх независимых URL, если корректно работает кнопка Back Telegram. Если потребуются прямые ссылки на секции, использовать маршруты `/`, `/support`, `/profile`.

### 7.2. Состояния интерфейса

Каждый экран с сетевыми данными должен иметь:

- загрузку;
- пустое состояние;
- ошибку с возможностью повтора;
- успешное состояние;
- блокировку повторной отправки во время мутации.

## 8. Функциональные требования

### 8.1. Главная

Главная показывает только активные тарифы в порядке, заданном администратором.

Начальный набор:

- 7 дней;
- 30 дней;
- 90 дней.

Карточка тарифа содержит:

- название;
- краткое описание, если задано;
- срок в днях;
- исходную цену;
- валюту;
- итоговую цену после применённого промокода;
- размер скидки, если применимо;
- кнопку покупки;
- визуальную отметку рекомендуемого тарифа, если задана.

Цена, валюта, срок и идентификатор тарифа не считаются доверенными, если пришли от клиента. Перед созданием заказа сервер получает тариф из базы заново.

### 8.2. Поддержка

Раздел содержит:

- список опубликованных FAQ;
- раскрывающиеся ответы;
- форму обращения;
- результат отправки с номером обращения.

Поля обращения:

- тема: 3–120 символов;
- сообщение: 10–4000 символов.

Сообщение администратору содержит:

- номер обращения;
- Telegram user ID;
- username, если доступен;
- имя пользователя;
- тему;
- текст;
- дату и время UTC.

Текст пользователя экранируется в соответствии с выбранным `parse_mode` Telegram, чтобы исключить поломку форматирования и нежелательные ссылки/упоминания.

### 8.3. Профиль

Профиль показывает доступные из проверенного Telegram `initData` данные:

- avatar/photo URL, если Telegram его передал;
- имя;
- фамилию, если доступна;
- username, если доступен;
- Telegram user ID — только при необходимости диагностики.

Отсутствующие username или avatar отображаются корректно: для аватара используется инициала/placeholder, username не выдумывается.

#### 8.3.1. Промокод

Профиль содержит поле ввода промокода.

Требования:

- нормализация регистра и пробелов выполняется на сервере;
- валидность проверяется на сервере;
- отображается тип и размер скидки без раскрытия внутренних ограничений;
- применение промокода не резервирует скидку навсегда;
- промокод повторно проверяется атомарно при создании и подтверждении заказа;
- итоговая сумма не может быть отрицательной;
- использование учитывается только для успешно оплаченного заказа.

#### 8.3.2. История покупок

Для каждой покупки отображаются:

- дата;
- тариф на момент покупки;
- исходная сумма;
- скидка;
- итоговая сумма;
- валюта;
- статус оплаты;
- статус выдачи VPN-доступа.

Исторические значения хранятся как snapshot в заказе и не меняются после редактирования тарифа.

#### 8.3.3. Активная подписка

Если подписка активна, отображаются:

- статус;
- дата начала;
- дата окончания;
- оставшееся время;
- Subscription URL;
- кнопка копирования;
- QR-код, содержащий тот же Subscription URL;
- краткая инструкция по подключению.

Если доступ оплачен, но Marzban временно недоступен, отображается состояние «Оплата получена, доступ создаётся» без предложения оплатить повторно.

Subscription URL считается секретом доступа:

- не записывается полностью в application logs;
- не передаётся сторонним аналитическим системам;
- не включается в URL страницы Mini App;
- показывается только владельцу после серверной авторизации.

### 8.4. Административный раздел

Ссылка на административный раздел видна в профиле только администратору. Серверные маршруты дополнительно защищены проверкой Telegram user ID.

#### 8.4.1. Тарифы

Поля:

- `name`;
- `description`;
- `durationDays`, целое число больше 0;
- `priceMinor`, целое число в минимальных денежных единицах;
- `currency`, код из поддерживаемого списка;
- `isActive`;
- `isFeatured`;
- `sortOrder`.

Операции:

- создание;
- просмотр;
- редактирование;
- деактивация;
- удаление только тарифа, который нигде не используется.

Если тариф связан с заказами, вместо физического удаления используется деактивация.

#### 8.4.2. Промокоды

Поля:

- уникальный `code`;
- тип скидки: `percent` или `fixed`;
- значение скидки;
- валюта для фиксированной скидки;
- дата начала;
- дата окончания;
- общий лимит использований;
- лимит на одного пользователя;
- опциональный список разрешённых тарифов;
- `isActive`.

Правила:

- процент: больше 0 и не больше 100;
- фиксированная скидка применяется только к совместимой валюте;
- лимиты проверяются внутри транзакции;
- удаление использованного промокода запрещено, доступна деактивация.

#### 8.4.3. FAQ

Поля:

- вопрос;
- ответ;
- порядок;
- признак публикации.

#### 8.4.4. Обращения

Администратор может:

- просматривать обращения;
- фильтровать по статусу;
- переводить между `new`, `in_progress`, `resolved`;
- видеть статус доставки Telegram-уведомления.

#### 8.4.5. Заказы и выдача доступа

Администратор видит:

- идентификатор заказа;
- пользователя;
- платёжный статус;
- внешний ID платежа;
- статус provisioning;
- последнюю безопасную ошибку;
- число попыток;
- время следующего повтора.

Кнопка повтора доступна только для оплаченного заказа в ошибочном состоянии. Операция остаётся идемпотентной.

## 9. Интеграция с Telegram

### 9.1. Аутентификация Mini App

Сервер обязан:

1. Получить исходную строку `initData`, а не доверять `initDataUnsafe`.
2. Проверить HMAC-подпись по алгоритму Telegram.
3. Проверить допустимый возраст `auth_date`.
4. Выполнить constant-time comparison подписи.
5. Провалидировать схему вложенного объекта `user`.
6. Использовать Telegram user ID как строку или 64-битное целое без потери точности.
7. После проверки создать серверную сессию в cookie.

Рекомендуемый максимальный возраст `initData` для создания сессии — 5 минут. Значение делается конфигурируемым.

Cookie сессии:

- `HttpOnly`;
- `Secure` в production;
- `SameSite=Lax`;
- ограниченный срок жизни;
- ротация после повторной аутентификации;
- случайный непрогнозируемый идентификатор;
- серверное отзывное состояние.

Разработка вне Telegram допускается только через явно включаемый development-only mock. В production mock-auth должен завершать запуск с ошибкой конфигурации.

### 9.2. Telegram Bot API

Bot token хранится только в серверной переменной окружения.

Бот используется для:

- отправки обращений администратору;
- опциональных уведомлений пользователю о готовности подписки;
- опциональных уведомлений администратору об ошибках provisioning.

## 10. Интеграция с Marzban

### 10.1. Общие требования

- Взаимодействие выполняется только серверным адаптером.
- Marzban API не публикуется в интернет без необходимости.
- Приложение обращается к Marzban по внутренней Docker-сети.
- Учётные данные Marzban не попадают в браузер, базу заказов или логи.
- Используется VLESS inbound, согласованный с эксплуатационной конфигурацией.
- Таймаут, ограниченное число повторов и backoff обязательны.
- Ответы Marzban проходят runtime-валидацию.

### 10.2. Идентификатор пользователя Marzban

Рекомендуемый формат: непрозрачный стабильный идентификатор, производный от локального UUID пользователя, например `tg_<short-uuid>`. Не использовать username Telegram: он необязателен и может измениться.

Локальная база хранит:

- `marzbanUsername`;
- `marzbanStatus`;
- `subscriptionUrl` в защищённом виде либо минимальные данные для безопасного получения;
- `expiresAt`;
- дату последней синхронизации;
- последнюю нормализованную ошибку.

### 10.3. Создание и продление

После подтверждения оплаты provisioning worker:

1. Блокирует конкретный заказ на обработку.
2. Проверяет, не был ли заказ уже применён.
3. Получает текущее состояние пользователя Marzban.
4. Рассчитывает ожидаемую дату окончания по серверным данным.
5. Создаёт или обновляет Marzban user.
6. Получает Subscription URL.
7. В одной локальной транзакции обновляет подписку и помечает заказ применённым.

Если внешний вызов успешен, а локальная транзакция не завершилась, повтор сначала сверяет фактическое состояние Marzban и не продлевает подписку вслепую.

### 10.4. QR-код

QR-код генерируется приложением из Subscription URL после серверной авторизации. Предпочтительно формировать SVG на сервере или локально в браузере без передачи ссылки внешнему QR-сервису.

### 10.5. Внешний контракт Marzban

Перед реализацией адаптера необходимо зафиксировать:

- конкретную версию или commit/tag образа Marzban;
- используемые endpoints и схемы ответов;
- способ сервисной аутентификации;
- имя VLESS inbound;
- правила `flow`, TLS/REALITY и лимита трафика;
- формат и срок жизни Subscription URL;
- поведение API при продлении истёкшего пользователя.

Все детали этого пункта имеют статус **TBD** до проверки OpenAPI конкретной развёрнутой версии Marzban.

## 11. Платежи через Stripe

### 11.1. Выбранная интеграция

Платёжный провайдер первой версии — **Stripe**. Используется Stripe Checkout в режиме одноразового платежа (`mode: payment`) со Stripe-hosted Checkout Page.

Приложение не собирает и не хранит данные банковских карт. Клиент получает от сервера только URL созданной Checkout Session и открывает его через поддерживаемый Telegram способ внешней навигации. После оплаты Stripe возвращает пользователя на `success_url`, однако возврат на эту страницу не является подтверждением платежа.

До production launch необходимо подтвердить:

- доступность Stripe для страны регистрации бизнеса и банковского счёта;
- прохождение Stripe account verification;
- допустимость VPN-сервиса правилами Stripe для конкретной страны и аккаунта;
- поддерживаемые валюты, минимальные суммы и способы оплаты;
- налоги, чеки, фискализацию и политику возвратов;
- фактическое поведение Stripe Checkout при открытии из поддерживаемых Telegram WebView.

Эти вопросы остаются **TBD** и проверяются с Stripe и профильным специалистом до приёма реальных платежей.

### 11.2. Создание Checkout Session

1. Сервер повторно загружает тариф и проверяет промокод.
2. Сервер создаёт локальный заказ со статусом `pending_payment`.
3. Сервер создаёт Stripe Checkout Session через официальный Stripe Node SDK.
4. В Stripe передаются вычисленные сервером сумма и валюта.
5. В `client_reference_id` передаётся непрозрачный ID локального заказа.
6. В `metadata` допускаются только минимальные несекретные идентификаторы: `orderId` и внутренний `userId`.
7. Для POST-запроса к Stripe используется стабильный idempotency key, связанный с одной попыткой создания Checkout Session.
8. Локально сохраняются `stripeCheckoutSessionId`, `stripePaymentIntentId`, если доступен, и срок действия сессии.

Нельзя передавать в Stripe metadata:

- Telegram `initData`;
- bot token;
- Subscription URL;
- данные доступа Marzban;
- полное содержимое обращения в поддержку;
- другие секреты или лишние персональные данные.

Повторное нажатие кнопки оплаты для того же открытого заказа возвращает существующую действующую Checkout Session либо создаёт новую контролируемую попытку после истечения предыдущей. Оно не создаёт несколько локальных заказов без явной необходимости.

### 11.3. Webhook Stripe

Endpoint: `POST /api/payments/stripe/webhook`.

Обязательные требования:

- использовать исходные байты тела запроса без предварительного JSON-преобразования;
- получить заголовок `Stripe-Signature`;
- проверить подпись официальным Stripe SDK и `STRIPE_WEBHOOK_SECRET`;
- отклонить запрос при неверной подписи или недопустимой временной метке;
- сохранить Stripe event ID с уникальным ограничением;
- обрабатывать одно событие не более одного раза;
- отвечать `2xx` только после надёжного сохранения принятого события;
- выполнять длительный Marzban provisioning вне критического пути webhook;
- не полагаться на порядок доставки событий.

Минимально обрабатываемые события:

- `checkout.session.completed`;
- `checkout.session.async_payment_succeeded`, если включены асинхронные методы;
- `checkout.session.async_payment_failed`, если включены асинхронные методы;
- `payment_intent.payment_failed`;
- `charge.refunded` или соответствующее событие возврата, выбранное после фиксации refund flow.

Для выдачи VPN проверяются как минимум:

- объект относится к ожидаемому Stripe account и live/test mode;
- `client_reference_id`/metadata соответствует существующему заказу;
- валюта и фактически уплаченная сумма совпадают с локальным заказом;
- платёж имеет подтверждённый Stripe-статус;
- заказ ещё не был применён к подписке.

Если данные расходятся, доступ не выдаётся, событие сохраняется для расследования, а администратор получает безопасный сигнал об ошибке.

### 11.4. Серверный Stripe-адаптер

Stripe SDK и secret key доступны только в `$lib/server`. Достаточно небольшого конкретного адаптера без универсальной фабрики провайдеров:

```ts
interface StripePayments {
  createCheckoutSession(input: CreateCheckoutInput): Promise<CheckoutSession>;
  verifyWebhook(rawBody: string, signature: string): VerifiedStripeEvent;
  retrieveCheckoutSession(sessionId: string): Promise<CheckoutSession>;
  refundPayment(input: RefundPaymentInput): Promise<RefundResult>;
}
```

Метод возврата реализуется только после фиксации продуктовой политики возвратов. Версия Stripe API фиксируется явно и обновляется контролируемо после проверки changelog и тестов.

### 11.5. Состояния

Заказ:

- `pending_payment`;
- `paid`;
- `provisioning`;
- `active`;
- `provisioning_failed`;
- `cancelled`;
- `refunded`.

Платёж:

- `pending`;
- `succeeded`;
- `failed`;
- `cancelled`;
- `refunded`.

Переходы выполняются только разрешёнными серверными командами. Webhook с уже обработанным внешним event ID возвращает успешный ответ без повторного применения.

### 11.6. Денежные значения

- Хранить только целые значения в минимальных денежных единицах: копейки, центы и т. п.
- Не использовать `number` с дробной частью для денежных расчётов.
- Валюта сохраняется вместе с каждой суммой.
- Заказ хранит snapshot названия тарифа, срока, цены и скидки.
- Итог пересчитывается сервером.
- Значения Stripe `amount_total`, `amount_subtotal` и currency сверяются с локальным заказом перед provisioning.

## 12. Архитектура приложения

### 12.1. Подход

Рекомендуется модульный монолит SvelteKit. Для одного разработчика это даёт минимальную операционную сложность, сохраняя разделение ответственности.

Слои:

- **routes/UI** — страницы, layouts, form actions и HTTP endpoints;
- **application** — use cases: создание заказа, применение промокода, подтверждение платежа, provisioning;
- **domain** — правила тарифов, скидок, заказов и подписок;
- **infrastructure** — Drizzle repositories, Telegram Bot API, Marzban adapter, payment provider;
- **shared** — схемы валидации, типы ошибок и безопасные утилиты.

SvelteKit server-only код размещается под `$lib/server`.

Пример структуры:

```text
src/
  lib/
    components/
    features/
      navigation/
      plans/
      profile/
      support/
      admin/
    server/
      auth/
      db/
      modules/
        users/
        plans/
        promo-codes/
        orders/
        subscriptions/
        support/
      integrations/
        marzban/
        payments/
        telegram/
      jobs/
    validation/
  routes/
    (app)/
    admin/
    api/
      auth/telegram/
      payments/webhook/
      internal/jobs/
```

Конкретная структура может быть упрощена, если модуль состоит из одного небольшого файла. Пустые слои и интерфейсы «на будущее» не создаются.

### 12.2. OOP и DRY

- OOP используется там, где объект инкапсулирует состояние или внешний контракт: адаптеры, сервисы, state machine.
- Простые преобразования и правила реализуются чистыми функциями.
- Наследование не используется без необходимости; предпочтительны композиция и небольшие интерфейсы.
- DRY применяется к знаниям и бизнес-правилам, а не к случайно похожим строкам кода.
- Допустима небольшая локальная дубликация, если общая абстракция сделает код сложнее.
- Доменные правила не дублируются между клиентом и сервером: клиентская проверка улучшает UX, серверная остаётся обязательной.

### 12.3. Серверные операции

- Чтение страницы выполняется через server `load`.
- Формы приложения по умолчанию используют SvelteKit form actions с progressive enhancement.
- Отдельные `+server.ts` endpoints используются для webhook, Telegram auth и контрактов, не являющихся обычными HTML-формами.
- Все входные данные проходят runtime-валидацию.
- Ошибки внешних систем преобразуются в стабильные внутренние коды.

## 14. SQLite и Drizzle ORM

- SQLite используется только для данных приложения. Marzban управляет собственной базой отдельно.
- Включить WAL mode, foreign keys и разумный `busy_timeout`.
- Все изменения схемы выполняются версионируемыми Drizzle migrations.
- Миграции запускаются отдельной одноразовой командой перед стартом новой версии приложения.
- Денежные значения и Telegram user ID не преобразуются в небезопасные JS-числа.
- Критические операции заказа, промокода и payment event выполняются в транзакциях.
- Для конкурентных webhook и provisioning используются уникальные ограничения, conditional update и короткие транзакции.
- Нельзя удерживать SQLite-транзакцию во время HTTP-запроса к Marzban или платёжному провайдеру.

SQLite подходит для первой версии и одного экземпляра приложения. Переход на PostgreSQL рассматривается, если подтверждены высокая конкуренция записей, несколько экземпляров приложения или требования высокой доступности.

## 15. Docker и размещение на одном сервере

## 16. Безопасность

### 16.1. Обязательные меры

- Проверка Telegram `initData` только на сервере.
- Server-side authorization для каждого ресурса.
- Runtime-валидация всех входных данных и внешних ответов.
- Параметризованные запросы через Drizzle.
- CSRF-защита для cookie-authenticated мутаций; использовать встроенные ограничения SvelteKit и проверять `Origin` для чувствительных endpoints.
- Проверка подписи и replay protection webhook.
- Rate limiting для auth, промокодов, поддержки, платежей и admin endpoints.
- Общие ошибки без утечки stack trace и секретов.
- Security headers: CSP, `X-Content-Type-Options`, `Referrer-Policy`, ограниченный `Permissions-Policy`, HSTS после корректной настройки HTTPS.
- Ограничение размера request body.
- Redaction токенов, cookie, webhook secrets, Subscription URL и персональных данных в логах.
- Зависимости проверяются на известные уязвимости перед релизом.
- Production source maps не публикуются без контроля доступа.

### 16.2. Секреты

Секретные значения:

- Telegram bot token;
- session secret/key;
- Marzban credentials;
- payment API key и webhook secret;
- ключ шифрования Subscription URL;
- приватные ключи Xray/REALITY.

Требования:

- только server-side env/secret files;
- `.env` не коммитится;
- в репозитории хранится `.env.example` без значений;
- разные секреты для development и production;
- ротация документируется;
- доступ выдаётся по принципу минимальных привилегий.

### 16.3. Персональные данные

Хранить только данные, необходимые для работы сервиса. До запуска определить:

- юрисдикцию;
- политику конфиденциальности;
- срок хранения пользователей, заказов, платежей, обращений и audit log;
- порядок удаления/анонимизации;
- требования к чекам и возвратам;
- законность предоставления и рекламы VPN-сервиса в целевых странах.

Эти вопросы имеют статус **TBD** и требуют консультации профильного специалиста.

## 18. Нефункциональные требования

### 18.1. Производительность

Целевые показатели первой версии при нормальной мобильной сети:

- серверный p95 для обычных read-запросов без внешних API — до 500 мс;
- p95 серверной мутации без внешних API — до 800 мс;
- первая полезная отрисовка — до 2,5 с на среднем мобильном устройстве;
- навигация и свайп — без заметных пропусков кадров;
- изображения оптимизированы, лишний JavaScript не загружается.

Provisioning и платежи не подчиняются этим значениям из-за внешних API, но UI сразу показывает промежуточное состояние.

### 18.2. Надёжность

- Повтор webhook безопасен.
- Повтор provisioning безопасен.
- Рестарт приложения не теряет оплаченные заказы.
- Временная недоступность Telegram или Marzban не приводит к потере локальных данных.

## 21. Топ-5 рекомендаций по SvelteKit

### 1. Использовать Svelte 5 runes для нового кода

- `$state` — только для изменяемого реактивного состояния;
- `$derived` — для вычисляемых значений;
- `$effect` — только для синхронизации с внешней системой или DOM, не для обычных вычислений;
- `$props` — для входных свойств компонентов;
- реактивную логику, которую нужно переиспользовать, выносить в `.svelte.ts`.

Это делает зависимости явными и уменьшает количество legacy stores и неочевидных `$:`-эффектов.

### 2. Держать доверенные операции на серверной стороне SvelteKit

Сессии, цены, скидки, admin checks, Marzban и платежи должны жить в `+page.server.ts`, `+server.ts`, server hooks и `$lib/server`. Компонент отвечает за интерфейс, а не за доверенную бизнес-логику.

### 3. Использовать server `load` для чтения и form actions для обычных мутаций

Form actions дают типизированный серверный POST, единый возврат ошибок и progressive enhancement. Самописный клиентский `fetch` использовать для webhook, нестандартного API или интерфейса, где form action действительно не подходит.

### 4. Использовать сгенерированные типы маршрутов и runtime-валидацию

Применять `PageProps`, `LayoutProps`, `RequestHandler`, `Actions` и типы из `./$types`. TypeScript не проверяет данные сети во время выполнения, поэтому границы Telegram, payment, Marzban, form data и env должны иметь runtime schema.

### 5. Минимизировать клиентское состояние и объём JavaScript

Данные страницы загружать через SvelteKit, состояние фильтров и выбранных представлений хранить в URL или локально рядом с компонентом. Не вводить глобальный store для данных, которые уже предоставляет серверный `load`. Lazy-load тяжёлые части админки и QR-библиотеку, не отключать SSR без измеримой причины.

## 24. Критерии приёмки

### 24.1. Авторизация и доступ

- Валидный пользователь Telegram входит без отдельной формы.
- Невалидный или устаревший `initData` отклоняется.
- Данные одного пользователя недоступны другому.
- Admin UI и endpoints недоступны пользователю с другим Telegram user ID.
- Изменение client-side user ID не даёт admin-доступ.

### 24.2. Интерфейс

- По умолчанию открывается «Главная».
- Поддержка расположена слева, профиль справа.
- Кнопки островка и свайп переключают секции.
- Активная секция очевидна.
- Навигация работает с клавиатуры и reduced motion.
- Glass-эффект имеет читаемый fallback.

### 24.3. Тарифы и промокоды

- Начальные тарифы 7/30/90 дней создаются seed-командой или через admin UI.
- Администратор может создать, изменить и деактивировать тариф.
- Исторический заказ не меняется после редактирования тарифа.
- Сервер игнорирует подменённую клиентом цену.
- Истёкший, выключенный или исчерпанный промокод не применяется.
- Лимит промокода корректен при конкурентных запросах.

### 24.4. Платёж и подписка

- Доступ не выдаётся по одному клиентскому redirect.
- Проверенный успешный webhook запускает provisioning.
- Повтор того же webhook не добавляет срок повторно.
- После успешного provisioning видны корректные QR и Subscription URL.
- При недоступности Marzban платёж сохраняется, заказ получает retryable status.
- После восстановления Marzban заказ можно завершить без повторной оплаты.

### 24.5. Поддержка

- FAQ отображаются в заданном порядке.
- Валидное обращение сохраняется и отправляется администратору.
- Ошибка Telegram Bot API не приводит к потере обращения.
- Пользовательский текст не ломает формат сообщения.

### 24.6. Эксплуатация

- Приложение поднимается по документированной Docker-команде.
- Внешне доступны только необходимые порты.
- Healthchecks отражают состояние сервисов.
- Backup создаётся и проверено восстановление.
- Логи не содержат секреты или полный Subscription URL.

## 26. Открытые вопросы и TBD

Блокируют production launch:

1. **Stripe production readiness:** страна и аккаунт, допустимость VPN-сервиса, валюта, способы оплаты, комиссии, возвраты, налоги/чеки и live webhook.
2. **Юрисдикция**, правила продажи VPN, privacy policy, retention и фискализация.
3. **Версия Marzban**, OpenAPI contract, authentication и VLESS inbound.
4. **Xray transport/security:** TCP/gRPC/WebSocket, TLS или REALITY, flow, домен и сертификаты.
5. **Лимит трафика:** безлимит либо quota для каждого тарифа.
6. **Домены**, DNS, reverse proxy и публичный доступ к Marzban admin.
7. **Продление:** разрешено ли несколько последовательных покупок и есть ли максимальный срок.
8. **Промокод:** можно ли сохранять выбранный код между сессиями и можно ли применять его ко всем тарифам по умолчанию.
9. **Поддержка:** достаточно ли одностороннего уведомления администратору или нужен ответ пользователю через бота.
10. **Уведомления:** отправлять ли пользователю сообщение после успешной выдачи/продления.
11. **Политика backup:** RPO, RTO, срок хранения и место внешней копии.
12. **Целевые Telegram clients** и минимальные поддерживаемые версии.

Не блокируют начало разработки:

- финальные тексты и иллюстрации;
- аналитика продукта;
- реферальная программа;
- расширенные роли администраторов;
